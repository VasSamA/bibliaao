"Backend call failure" ao abrir /biblia Transitório — sem ação necessária

2026-07-11

Sintoma

Página /biblia em produção mostrou o texto simples "Backend call failure" em vez da lista de livros.

[Print fornecido pelo utilizador no chat, mas não guardado como ficheiro — para o inserir aqui, guardar em docs/erros-screenshots/2026-07-11-backend-call-failure.png e substituir este bloco por <img class="screenshot" src="erros-screenshots/2026-07-11-backend-call-failure.png">.]

Procedimento seguido

  1. Testar a API diretamente: GET /api/v1/biblia/versoes → devolveu 200 com os dados corretos. A API estava saudável.
  2. Recarregar a página de produção diretamente no browser → carregou normalmente, sem erro.
  3. Confirmar réplicas da Container App (az containerapp replica list) → 1 réplica, Running, sem reinícios desde o último deploy.

Causa

Não reproduzida — provável timeout pontual de rede entre a Static Web App e a Container App no momento exato do pedido (cold start ocasional, ou pico de latência). Não houve crash nem reinício da API.

Ação

Nenhuma — recarregar a página resolve. Ver "Procedimento geral" no fundo deste documento para os passos a seguir se voltar a acontecer e não desaparecer ao recarregar.

Outage total da API — DATABASE_URL dessincronizado Resolvido

2026-07-11

Sintoma

Todos os endpoints da API a devolver 500 — Erro interno do servidor.

Procedimento seguido

  1. Logs da Container App (az containerapp logs show ... --tail 300) → PrismaClientInitializationError, código P1000: "Authentication failed... for biblia_admin are not valid".
  2. Verificado o Activity Log do resource group (az monitor activity-log list) → duas operações Microsoft.DBforPostgreSQL/flexibleServers/write pouco antes do outage — a password do Postgres tinha sido mudada diretamente no servidor.
  3. Gerada password nova alfanumérica, aplicada no servidor (az postgres flexible-server update --admin-password) e no secret database-url da Container App (az containerapp secret set) + reinício da revisão.
  4. Continuou a falhar mesmo depois disto — diagnóstico mais fundo: az containerapp show --query "properties.template.containers[0].env" revelou que o env var DATABASE_URL real do container era um valor literal fixo (não uma referência ao secret database-url). O secret existia mas nunca tinha sido lido por nada.
  5. Corrigido com az containerapp update --set-env-vars "DATABASE_URL=secretref:database-url".

Causa raiz

Duas causas empilhadas: (1) a password do Postgres foi alterada sem atualizar onde quer que fosse consumida; (2) o env var DATABASE_URL nunca esteve realmente ligado ao secret — provavelmente um resquício de uma versão anterior do Bicep. Agravante: duas sessões de Claude Code em paralelo (uma na Cloud Shell, outra local) mudaram a password de forma independente sem coordenação, o que atrasou o diagnóstico.

Ação / prevenção

Sempre que mudar a password do Postgres, confirmar com o comando do passo 4 acima que o env var está mesmo em modo secretref antes de dar o problema por resolvido. Não correr duas sessões a mexer na mesma infraestrutura de produção ao mesmo tempo.

Importação bíblica bloqueada — Midvash API atrás de Cloudflare Resolvido (via mudança de fonte)

2026-07-11

Sintoma

POST /biblia/importar/ara devolvia sempre "iniciada", mas a versão ficava presa em 1 livro (dados de exemplo), nunca progredia.

Procedimento seguido

  1. Logs da Container App filtrados por "falhou" → Midvash API erro 403 em /versions/ara, corpo da resposta era uma página de desafio Cloudflare ("Just a moment...").
  2. Confirmado que o bloqueio acontecia logo no primeiro pedido (metadados da versão), não durante a importação livro-a-livro — ou seja, nunca chegava a importar nada.
  3. Decisão: mudar a fonte de dados em vez de tentar contornar o bloqueio Cloudflare.

Causa raiz

A Midvash API passou a exigir um desafio JS/Cloudflare que nem a Container App nem a Cloud Shell conseguem resolver (não são um browser real).

Ação

Nova via de importação (usfx-import.service.ts) a partir de um ficheiro USFX de domínio público (repositório seven1m/open-bibles), com um único fetch em vez de um pedido por capítulo. Confirmado com 66/66 livros importados sem falhas.

Nenhum erro corresponde à pesquisa.

Procedimento geral quando a API/site falha

  1. Testar a API diretamente: GET https://biblia-production-api.victoriousplant-a5611e3c.westeurope.azurecontainerapps.io/api/v1/biblia/versoes. Se devolver dados → o problema é pontual/rede, recarregar a página.
  2. Ver logs: az containerapp logs show --name biblia-production-api --resource-group rg-bibliaao --tail 300 (máximo 300 por chamada).
  3. Ver saúde das réplicas: az containerapp replica list --name biblia-production-api --resource-group rg-bibliaao -o table — CrashLoopBackOff = está mesmo a cair.
  4. Documentar aqui, com o mesmo formato das entradas acima, seja qual for o resultado.
